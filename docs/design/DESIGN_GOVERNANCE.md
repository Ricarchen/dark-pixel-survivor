## 1. 目的

本规范解决四个长期问题：

1. 对话越来越长时，已确认细节不能依赖记忆保存。
2. 宏观设计、系统规则、角色内容与关卡节奏不能互相覆盖职责。
3. 建议、示例和原型事实不能被误写成最终规则。
4. 一项规则改变后，必须能够找到所有受影响报告并同步复核。

今后每份正式设计报告都必须能够独立回答：它设计什么、为什么这样设计、完整流程如何运行、与哪些系统交互、哪些内容已经确认、哪些仍待讨论、如何验证它没有偏离整体游戏。

## 2. 文档层级与权威边界

| 报告层级 | 权威负责内容 | 不得自行改变 |
|---|---|---|
| 宏观设计 | 产品愿景、核心支柱、全局不变量、系统职责、内容包结构 | 具体节点、局部数值、单个角色例外 |
| 决策账本 | 已确认、待定、已替代和已废止决策的稳定编号 | 用摘要替代完整系统流程 |
| 系统详细报告 | 通用流程、状态变化、规则、数据契约、接口、验证标准 | 某个角色剧情或未经登记的专属例外 |
| 角色内容包 | 角色身份、专属网络、专属武器与关卡引用、具体配置 | 重定义通用系统 |
| 关卡报告 | 阶段节奏、遭遇、机会预算、故事投放与构筑检验 | 发明新的升级、继承或武器规则 |
| 原型验证记录 | 已实现行为、测试结果、性能与体验证据 | 自动升级为目标设计定案 |

发生冲突时不能简单采用“更具体者优先”。必须在决策账本中新增或修订决策，更新设计基线，再同步所有受影响报告。

## 3. 三条状态轴

每条规范性内容同时声明三类状态，避免把“已实现”误认为“已确认”。

### 3.1 决策状态

- **提案**：可供讨论，不得作为后续系统的硬前提。
- **待定**：问题和边界已明确，但答案尚未确认。
- **已确认**：经过用户确认，可进入正式规格。
- **已替代**：曾经有效，现由新的决策 ID 取代。
- **已废止**：明确否定，仅保留以防旧方案回流。

**剧情待定**是“待定”的限定写法，表示答案依赖具体剧情或角色主题；它不是已确认的通用规则。

问题记录可以另用**已解决**或**部分解决**表示处理进度，不能将其当作新增决策状态。已解决的问题须指向对应已确认决策；部分解决的问题须分别写明已确认部分的稳定 ID 和仍待定的边界，不能把同一问题中的未回答部分一并升级为已确认。

### 3.2 内容类型

- **规则**：系统必须遵守的规范。
- **目标**：希望达到的体验或结果，仍需验证。
- **事实**：当前代码、资产或外部状态的可核查描述。
- **假设**：为了推进讨论而暂时采用的前提。
- **示例**：用于解释规则，不自动构成数量或数值定案。

**历史原型事实**属于内容类型“事实”的范围限定，不是决策确认状态。历史行为可以作为证据或参考，但只有经过重新确认的目标规则才能进入正式规格；历史事实本身不因此变为提案、废止规则或已确认玩法。

### 3.3 实现状态

- **未实现**
- **原型验证**
- **部分实现**
- **已实现**
- **已验证**
- **不适用**

## 4. 规则刚性

每条正式规则还应注明其刚性：

- **全局不变量**：所有内容必须遵守，例如 S 锻造不能创造新规则。
- **默认规则**：通常采用，但可通过登记例外改变。
- **逐内容配置**：角色、武器或关卡分别设定，例如母路线数量。
- **显式例外**：只对指定对象、条件和版本生效。

示例数量不得伪装成全局上限。“约五条路线”“三选一”“四把 A”若未正式确认，必须标记为示例或待定。

文档版本采用语义化形式：

- 修订号：措辞、链接或不改变规则的澄清。
- 次版本：新增已确认规则、完整流程或待定模块。
- 主版本：改变系统职责、核心循环或大量下游接口。

## 6. 系统详细报告标准结构

一份系统报告至少包含：

1. 执行摘要与玩家体验目标。
2. 职责边界：负责、不负责、相邻系统接口。
3. 术语与正交概念。
4. 输入、进入条件和内容来源。
5. 主流程与状态变化。
6. 接受、拒绝、中止、失败与退出路径。
7. 带稳定 ID 的规则表。
8. 全局不变量、默认规则、可配置项与例外。
9. 标准局与无尽模式中的职责。
10. UI、信息披露与表现要求。
11. 引擎无关的数据字段与系统接口。
12. 可观察的验证问题与测试不变量。
13. 风险、待定项和依赖问题。
14. 已替代／已废止规则摘要。
15. 修订历史。

“详细”不是提前填入所有数值。若数值未确认，应完整写明它影响什么、由哪个未来决策确定、确定前哪些边界不可突破。

## 7. 单条决策记录标准

规范性决策建议采用以下字段：

```text

```

语义发生实质改变时，旧 ID 标为“已替代”并链接新 ID；只有纯措辞澄清才沿用原 ID。

## 8. 来源与确认记录

当前对话是最初设计来源。正式入库后采用以下来源写法：

- `CONV-YYYYMMDD-NN`：一次对话确认批次。
- `DOC-<ID>@<version>`：来自另一份权威文档。
- `PROTO-<commit>`：来自旧原型的事实或验证证据。
- `TEST-<ID>`：来自可复现测试。

来源只证明内容从哪里来，不改变决策状态。原型代码存在某行为，并不等于目标游戏必须继承该行为。

仓库不保存完整对话转录时，交接文件应为最近确认批次提供可读摘要，并明确哪些规则只能追溯到旧账本、仍需未来审计。来源编号不能仅作为“已经确认”的循环证明；若新模型发现规则比可核查来源更具体，应保留原记录、标记审计风险，并向用户核对，而不是静默扩写或删除。

## 9. 例外登记

角色、武器或关卡需要突破默认规则时，必须创建 `EXC-*` 记录，写明：

- 适用对象与版本；
- 被突破的规则 ID；
- 剧情或机制理由；
- 生效条件与失效条件；
- 对角色、武器、关卡、UI、存档和测试的影响；
- 复核时机。

例外不能突破全局不变量；若必须突破，应先修改宏观设计和设计基线。

## 10. 引擎无关的数据最低要求

技术框架未锁定前，系统报告至少定义以下逻辑字段，而不绑定具体类名：

- 稳定运行时 ID、显示名本地化键、类型与子类型；
- 所属系统、角色包、武器家族或关卡包；
- 前置、后继、互斥、融合与依赖 ID；
- 发出和监听的公开事件／标签；
- 触发条件、输入、状态变化、输出、冷却或生命周期；
- 参数名、单位、默认值、允许范围与成长曲线；
- 解锁条件、候选池资格与随机权重来源；
- 持久范围：本局、局外横向解锁或纯叙事；
- 表现资源引用与信息披露要求；
- 数据版本、迁移要求和验证 ID。

## 11. 跨文档变更流程

1. 对话期间临时累计用户逐项确认，并持续区分已确认、助手提案和未回答问题。
2. 完成一个连贯章节，或用户明确要求“整理／保存／上传”时，才启动一次文档批次。
3. 在决策账本将该批已确认内容分配稳定 ID；未回答的最后问题必须进入待定项，不能因紧邻确认而自动升级。
4. 更新权威系统报告的流程、边界和数据契约。
5. 在追踪矩阵登记所有下游角色、武器、关卡与测试。
6. 同一批次复核所有受影响文件、旧措辞和当前讨论坐标。
7. 更新设计基线、交接摘要与修订历史。
8. 一批确认对应一次集中提交；不为每一句“同意”单独创建 GitHub 提交。

## 12. 报告完成度验收清单

一份报告只有满足以下条件，才可标记为“已审阅”：

- [ ] 元数据、职责和版本完整。
- [ ] 每条规范性内容均有状态；建议和示例没有伪装成定案。
- [ ] 所有待定项都写明依赖或下一决策问题。
- [ ] 已替代规则能够双向追踪，新文档不再引用旧规则。
- [ ] 主流程包含进入、选择、成功、拒绝、失败和退出路径。
- [ ] 全局不变量、默认规则、逐内容配置和例外已经区分。
- [ ] 内容规模区分目标值、允许范围、硬上限和示例。
- [ ] 标准局与无尽模式中的职责均可解释。
- [ ] UI 能在选择前说明永久损失、继承、其他状态变化和风险。
- [ ] 数据字段足以保存、复现和迁移完整状态。
- [ ] 跨系统协同只通过公开接口，不混合系统职责。
- [ ] 每项核心承诺至少有一个可观察验证问题。
- [ ] 追踪矩阵已更新。
- [ ] 没有未解释的 `TODO`、`TBD` 或含糊占位符。

## 13. 通用验证问题

- 单条角色母路线和单把正式武器能否独立成立？
- 未获得目标随机路线时，构筑能否继续而非直接报废？
- 跨系统协同是否只通过公开事件、标签和契合接口？
- 例外是否引入了隐藏专用资源或破坏全局支柱？
- 关卡提供的机会数量是否支撑预期成长弧线？
- 玩家能否在确认选择前理解获得、失去、状态变化与风险？
- 相同随机种子和输入能否重放关键候选与状态变化？

## 14. 当前执行约定

- 宏观目标以 `TARGET_GAME_DESIGN.md` 为权威入口。
- 逐条决策以 `GAME_ARCHITECTURE.md` 为权威账本。
- 角色网络通则以 `systems/CHARACTER_EVOLUTION_NETWORK.md` 为权威系统报告。
- 武器通则以 `systems/WEAPON_SYSTEM.md` 为权威系统报告。
- 原型边界以 `legacy/README.md` 为准。
- 跨文档依赖与复核状态维护在 `DESIGN_TRACEABILITY.md`。
- 新模型或新任务的接手入口以 `DESIGN_HANDOFF.md` 为准，但交接摘要不能覆盖上述权威文档。

后续只有在真正开始设计对应内容时才创建角色或关卡报告，不提前生成大量空壳文件。

## 15. 模型交接规范

交接文件至少包含：当前提交与设计基线、权威阅读顺序、最新确认批次、仍待定问题、已废止方向、已知审计风险和用户工作偏好。

接手模型必须先做只读审计：检查 Git 状态、文档版本、确认／待定边界、旧原型隔离和跨系统职责。发现矛盾时先报告证据，不能为了继续提问而假装文档一致。审计完成后，每次只推进一个真正未决的设计问题；提供可比较方案和推荐，等待用户确认。除非完成一个章节或用户明确要求，不应在每轮对话后修改或提交 GitHub。
